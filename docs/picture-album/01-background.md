# 01 · 产品背景与历史决策

## 1. 项目现状回顾

「云端图库」上线三个月，核心是一面公开图片墙：用户无需登录即可上传图片、以瀑布流/网格浏览、下载与删除。技术形态为前后端分离：

- 前端：Vue 3（Composition API + `<script setup>`）+ WindiCSS + Vite。
- 后端：Spring Boot 2.7，运行在 Java 8 环境；MySQL 8 存储元数据；图片文件落在服务端 `images/` 目录。
- 部署：`docker-compose` 一键编排前端、后端、数据库。

现有能力仅覆盖「单张图片」维度，随着单个用户上传量增长（内测用户平均已上传 300+ 张），"找图难""无法归类"成为最集中的反馈。

## 2. 用户反馈摘录（内测问卷，节选）

> "图片越来越多，想把某次旅行的照片放一起，但只能一整面墙往下翻。"（受访者 A）  
> "我希望同一张图能既在'风景'又在'壁纸'里，不想上传两遍。"（受访者 B）  
> "整理相册时误删了一整个分组，结果原图也没了，太吓人。"（受访者 C）  
> "封面老是乱跳，昨天设的封面今天自己变了。"（受访者 D，针对早期灰度版本）  
> "选中一堆图想一起塞进相册，只能一张张点，很累。"（受访者 E）

这些反馈直接催生了后续的相册（Album）项目，也解释了为什么下文对**「移出 ≠ 删除」**、**「一图多相册」**、**「封面可控且稳定」**、**「批量操作」**格外强调。

## 3. 相册项目的目标

1. 在不改变图片物理存储的前提下，提供**逻辑分组**能力（相册）。
2. 支持**一张图片属于多个相册**（多对多）。
3. 相册要有**稳定、可控的封面**与**可自定义的图片顺序**。
4. 支持**批量**把图片加入 / 移出相册。
5. 全过程**不能危及原始图片数据安全**。

## 4. 硬性历史决策（HD 系列）

以下决策在立项评审时确定，属于长期约束。除非 `05-change-log.md` 中有更新的 FINAL 条目推翻，否则一律有效。

- **HD-1（数据安全红线）**：相册是图片之上的「视图」。**删除相册、从相册移出图片，都绝不能删除图片文件或图片记录。** 只有图库层面的「删除图片」才允许物理删除。此条为最高优先级，任何功能设计与之冲突时以此为准。
- **HD-2（一图多相册）**：成员关系是**多对多**。严禁通过"给 Picture 加一个 albumId 字段"或"复制一份图片记录"来实现分组——那样无法表达一图多属，且会制造脏数据。
- **HD-3（封面必须是成员）**：相册封面只能取自该相册当前成员；一旦封面对应的图片被移出相册或在图库中被删除，封面必须自动失效并回退。
- **HD-4（端口不变）**：相册项目属于增量迭代，**沿用现有端口**，不得为新功能改动对外端口。具体端口值见 `04-engineering-guide.md`。
- **HD-5（增量交付）**：在现有 `picture-backend` / `picture-frontend` 工程内扩展，不新建平行工程，不推翻现有上传 / 列表 / 下载 / 单图删除主流程。

## 5. 一个早期误区（仅历史参考，DEPRECATED）

立项初期曾有人提出"最简实现"：在 `Picture` 上直接加一个字符串字段 `albumName`，用逗号分隔多个相册名。该想法在第一次技术评审就被否决，原因：无法重命名相册、无法维护封面与顺序、检索性能差、极易产生脏数据。

> ⚠️ 该 `albumName` 逗号分隔方案**已废弃，禁止实现**。保留在此仅用于说明为什么最终采用独立的多对多成员关系。正式建模见 `02-requirements.md` 与 `03-api-contract.md`，最终结论见 `05-change-log.md`。
